# Как снизить время и память в `soup train`: анализ и идеи

**Главный вывод.** Конфигурация 505 MiB близка к пределу по памяти, основной резерв теперь во времени.
Реалистичная цель для одной конфигурации: **47–52 с при 440–480 MiB**. Самый сильный кандидат нашёлся
в наших старых замерах: `gate_proj` и `up_proj`, похоже, лежат в невыгодной для cuBLAS раскладке.

**На чём основан анализ.** Чтение кода, логи `kaggle_out/`, регрессии по `metrics.json`.
На GPU ничего не запускалось, код в этом документе не исполнялся.

**Метки:**

- **[изм]** — наши замеры на T4;
- **[вывод]** — расчёт по замерам;
- **[оценка]** — предположение.

Замеры сделаны на разных машинах и коммитах, поэтому абсолютные секунды сравнивать напрямую нельзя.

## 1. Модель затрат

### 1.1. Шаг обучения

Токены на шаг [изм]: среднее 832, медиана 775, максимум 1427. Метки есть у 63,5% токенов.

Время шага разложено как `a + b·N` по парам (шаг, число токенов), шаги с 3-го:

| Конфигурация | Прогон | a, мс | b, мс/токен | R² |
|---|---|---:|---:|---:|
| База | `fl/rt1/base_1` | 196 | 0,80 | 0,72 |
| Скорость, 6793 MiB | `fl/rt1/solution_1` | 35 | 0,42 | 0,98 |
| Кэш fp16, 4151 MiB | `full/solution_1` | 146 | 0,35 | 0,94 |
| Budget 256, ~950 MiB (старый коммит) | `cmd/r_256_1` | 112 | 0,60 | 0,96 |
| Budget 0, 673 MiB (старый коммит) | `cmd/r_0_0` | 190 | 0,59 | 0,93 |
| Группы по 512, 429 MiB | `fl/rm1/solution_1` | 271 | 0,97 | 0,76 |

Что из этого следует [вывод]:

- В скоростной конфигурации шаг почти целиком зависит от числа токенов. При `a` = 35 мс Python в основном
  прячется за работой GPU. Это согласуется с A/B, где удаление 1300 запусков ничего не дало.
- В конфигурации с пересчётом постоянная часть составляет 110–190 мс. В неё входят распаковка NF4
  (46 мс при трёх проходах), PCIe-обход таблицы головы (37 мс) и накладные расходы.

Профиль шага 505 MiB (профилировщик, 16 шагов, `runtime_summary.json`) [изм]:

| Статья | мс/шаг |
|---|---:|
| Матмулы | 221 |
| HtoD (побочный поток, частично параллельно счёту) | 144 |
| Распаковка NF4 | 46 |
| Касты, attention, поэлементные, dropout, SwiGLU, RMSNorm и прочее | около 115 |
| Простой GPU при медиане шага 0,503 с [вывод] | около 110 |

Физические пределы:

- **PCIe против пересчёта.** PCIe даёт 12,4 ГБ/с [изм]. Перенос `gate` и `up` стоит 36 КБ на токен,
  то есть около 5,8 мкс на токен туда и обратно. Пересчёт стоит около 2,7 мкс на токен.
  **Пересчёт выгоднее выгрузки активаций**, что совпадает с замером 58 с при 2215 MiB.
- **Распаковка NF4.** Читается 0,5 и пишется 2 байта на значение. Сейчас это около 66% от оценки предела
  памяти в 320 ГБ/с, поэтому больших резервов в самом кернеле нет.
- **Таблица головы.** 445 MiB по PCIe занимают не меньше 36 мс на шаг. При N ниже примерно 1000 обход
  упирается в копирование, а не в GEMM [вывод].

### Как проверять все идеи

Батчи в прогонах одинаковые, поэтому сравнивать надо **попарно по шагам**: медиана `step_s_B / step_s_A`
на шагах 3–64 в порядке ABBA в одной сессии. Такой метод устойчивее к разбросу машин, чем общее время.
Перед сдачей любая идея проходит полный прогон `--repeats 2` со всеми 10 проверками.

### Идея 1. Раскладка весов `gate` и `up`

**Механизм.** В одной сессии `mindx-research` [изм]:

- `M830 K1536 N8960` занял 0,602 мс (38 TFLOPS);
- весь слой при N=830 занял 3,86 мс.

Если сложить по этим цифрам, получится 2,89 мс: 0,602 × 2 + 1,104 (`down`) + 0,258 × 2 (q, o) + 0,034 × 2 (k, v).
Разница 0,97 мс означает, что `gate` и `up` в реальном пути идут примерно по 1,09 мс.
`sweep` с `w.t()` даёт для них 1,11 мс при N=832.

Почему так может быть [вывод]. `F.linear(x, W)` при `W` в row-major даёт вызов `tn`, а `x @ B` при `B` в row-major даёт `nn`:

| Форма | Где встречается | `tn` | `nn` |
|---|---|---:|---:|
| `K1536 N8960` | forward `gate` и `up`, backward `down` | 1,11 мс | 0,60 мс |
| `K8960 N1536` | backward `gate` и `up`, forward `down` | 0,96 мс | 1,10 мс |

Значит, `gate` и `up` могут быть в худшей раскладке в обе стороны, а `down` в лучшей.

**Важное ограничение.** Исходник бенчмарка `mindx-research` потерян, а числа `tn` и `nn` для `K8960` взяты из
разных сессий. Причина в раскладке — вывод, а не прямой замер. При N=2048 разрыв меньше: 1,75 против 2,18 мс
(в 1,25 раза). `floor_bench.py gemm` по логам не запускался.

- **Точка патча:** `NF4StreamFunction` в `solution/linear4bit.py` и новый кернел распаковки, который сразу пишет `W^T`.
- **Расчёт:** выигрыш при N̄=832 составляет `28·2·2·(0,25…0,5)` мс на forward и около 8 мс на backward.
  За вычетом замедления распаковки это 25–60 мс/шаг.
- **Что может сломаться:** младшие биты GEMM могут отличаться (проверки 5–7, риск низкий). Новый кернел
  добавит компиляцию, его нужно прогревать в `warmup`. Переход `N` между раскладками может оказаться ступенчатым.
- **Дешёвая проверка:** скрипт ниже, около минуты на T4.
- **Провал:** выигрыш `gate` и `up` меньше 10% при N от 640 до 1430.

Голову этот приём почти не ускорит: при типичных N она упирается в копирование по PCIe.

### Идея 2. Мёртвые значения в пересчёте

**Механизм.** Обратному проходу не нужно значение выхода линейной операции. В повторном прогоне выходы
`down_proj` и `silu·up` никто не читает, поэтому их можно не считать. Новый буфер границы слоя для этого не нужен.

- **Точка патча:** `Qwen2MLP.forward`, ветка `_in_backward()`.
- **Расчёт:** GEMM `down` 19–29 мс, его распаковка 4 мс, forward `silu` 4 мс, касты и Python 3–8 мс.
  Итого 30–45 мс/шаг.
- **Что может сломаться:** проверки 5–7 только при ошибке в градиенте, ведь первый проход не меняется.
  Доля кернелов (проверка 4) немного сместится, запас большой: 13–23%.
- **Дешёвая проверка:** градиенты LoRA с патчем и без него на маленькой модели. Они должны совпасть бит в бит.
- **Провал:** выигрыш меньше 1 с в парном A/B.

Можно пойти дальше и сохранять на хосте ещё и вход второй нормы, чтобы пропустить `o_proj`. Это ещё около 5 мс/шаг,
но добавляет копии, поэтому сначала стоит сделать простой вариант.

### Идея 3. Первый шаг и старт конфигурации памяти

**Механизм.** Первый шаг занимает 1,8–2,1 с против 0,7 с в скоростном профиле [изм]. Вероятные причины:

- `LayerStreamer.__init__` ещё раз копирует веса в pinned-память прямо перед первым шагом;
- в py-spy часть кернелов компилируется в потоке autograd, значит `warmup` покрывает не все варианты
  (видно на скоростном профиле).

**Что сделать:**

1. Снять `tools/floor_spy.py` на `rules_memory`.
2. Дополнить `warmup` недостающими вариантами.
3. Запускать `stream.setup` в потоке сразу после `_setup_transformers`, чтобы он шёл параллельно `Dataset.map`.

- **Серая зона:** организаторы прямо разрешили поток для компиляции и предчтения весов, а для этой работы
  разрешения нет. Риск низкий, но лучше спросить.
- **Что может сломаться:** проверка 1 при гонке, если главный поток не дождётся завершения потока.
- **Дешёвая проверка:** поле `step_s[0]` и разница `wall − train_loop`.
- **Провал:** меньше 0,5 с.

### Идея 4. Меньше распаковок между пересчётом и backward

**Механизм.** Веса `up`, а при коротких батчах и `gate`, можно оставить распакованными до их backward.
Для `up` пик не растёт: он и так проходит через тот же набор буферов. `gate` можно держать при N≲900 (около 70% батчей).

- **Что может сломаться:** проверка 8 по памяти, если порог выбран неверно.
- **Проверка:** пик остаётся прежним при N=1427.
- **Провал:** пик вырос.

### Идея 5. Паддинг «невыгодных» N

**Механизм.** Время GEMM зависит от N немонотонно [изм]: для одного и того же веса N=320 медленнее 384,
896 медленнее 1024, 1600 медленнее 1664. Разрешено правилом QA 48. Для каждой формы веса нужна небольшая таблица.

- **Что может сломаться:** почти ничего, но на самых длинных батчах паддинг нужно отключать, иначе вырастет пик.
- **Провал:** выигрыш в реальном слое меньше 3%.

### Идея 6. Отложенная подкачка второго слота

**Механизм.** На длинных батчах следующий слой можно начинать копировать только после MLP-части backward текущего.
Именно они задают пик, и у них хватает времени на копию.

- **Что может сломаться:** короткие батчи могут начать ждать копию, поэтому поведение должно зависеть от N.
- **Провал:** время растёт больше чем на 0,5 с.

### Идея 7. Состояние AdamW в pinned-памяти

**Механизм.** Состояние Adam не нужно на пике backward. Его можно поднимать на GPU только на шаг оптимизатора.
Копии примерно по 1,8 мс должны скрываться за другой работой. Разрешено организаторами.

- **Что может сломаться:** порядок обновления параметров (проверки 6–7).
- **Провал:** время +0,5 с или изменение eval loss.

### Идея 8. Лишнее в голове и dropout

**Механизм:**

- `torch.mm(buf, w)` в `head_stream.py` идёт и по строкам без меток, где `buf` нулевой. Это 36,5% токенов [изм].
  Если поставить размеченные строки вперёд, экономия составит около 5 мс/шаг.
- Маски dropout можно не рисовать заново в пересчёте, а сохранить битами. Экономия около 6 мс/шаг.

- **Что может сломаться:** порядок строк и маски (проверка 5).
- **Проверка:** совпадение бит в бит.

## 4. Самая неочевидная идея

Это идея 1. Обычно cuBLAS считают чёрным ящиком: профиль показывает «упёрлись в матмулы», и оптимизация заканчивается.
Здесь же одни и те же FLOPs, похоже, стоят в 1,25–1,85 раза больше только из-за физической раскладки весов.
NF4 при этом остаётся, а поскольку веса всё равно распаковываются на каждом проходе, раскладку можно выбрать прямо в кернеле.

## 5. Что не стоит делать

| Идея | Почему нет |
|---|---|
| Группы строк ради памяти ниже 430 MiB | 91–99 с [изм], наклон растёт на 60% |
| Полная выгрузка активаций на хост | Физика против неё, замер 58 с при 2215 MiB |
| Убирать Python и сокращать запуски | A/B ничего не дал, а `a` всего 35 мс |
| Средние конфигурации между 1 и 4 ГБ | Лестница 1077–4149 MiB дала только 55 → 48,6 с [изм] |
| int8 в forward | Ломает проверку 6 [изм] |
| int8 только в пересчёте | Выход int32 и лишние проходы съедают выигрыш, остаётся около −24 MiB ценой риска для качества [оценка] |
| Свой NF4 + `mma` на inline PTX | Предел около −3 с при большом риске |
| CUDA graphs для шага | 0% при ~1000 токенах [изм], их кернелы не идут в долю |
| Более дешёвый ключ кэша Triton | В логах нет ожидания потока компиляции, выигрыш около 0 |
| Общий префикс строк в батче | Маски dropout у строк разные, значения изменятся |
| Энтропия по части токенов, усечённый словарь | Нарушает QA 35, это уже другая задача |
| `gc.disable` | Серая зона после запрета `gc.freeze`. Можно только замерить через `gc.callbacks` и спросить организаторов |

## 6. Код для двух сильнейших идей

Код не запускался: локально нет GPU. Перед использованием его нужно проверить тестами на T4.

### 6.1. Идея 1: сначала бенчмарк

```python
# tools/bench_layout.py
import torch


def timed(fn, reps=20):
    for _ in range(3):
        fn()
    start = torch.cuda.Event(enable_timing=True)
    end = torch.cuda.Event(enable_timing=True)
    start.record()
    for _ in range(reps):
        fn()
    end.record()
    torch.cuda.synchronize()
    return start.elapsed_time(end) / reps


w = torch.randn(8960, 1536, dtype=torch.float16, device="cuda")
wt = w.t().contiguous()  # [1536, 8960], row-major
print(f"transpose copy {timed(lambda: w.t().contiguous(), 5):.3f} ms")
for n in (354, 512, 640, 775, 832, 1024, 1296, 1430):
    x = torch.randn(n, 1536, dtype=torch.float16, device="cuda")
    g = torch.randn(n, 8960, dtype=torch.float16, device="cuda")
    print(n,
          f"fwd {timed(lambda: torch.mm(x, w.t())):.3f} -> {timed(lambda: torch.mm(x, wt)):.3f}",
          f"bwd {timed(lambda: torch.mm(g, w)):.3f} -> {timed(lambda: torch.mm(g, wt.t())):.3f}",
          flush=True)
```

Если гипотеза подтвердится, A/B сначала можно сделать через `.t().contiguous()`. Это даёт +26 MiB, но требует всего
несколько строк. В финальной версии лучше сразу писать `W^T` в кернеле, для `W` с кратными 64 размерами:

```python
@triton.jit
def nf4_unpack_t_kernel(packed_ptr, out_ptr, nf4_ptr, absmax_ptr, code_ptr, absmax2_ptr,
                        offset_ptr, blocks_per_row, rows):
    # One program: 64 rows x one block (64 columns) of W; out[col, row] is W^T.
    row = tl.program_id(0) * 64 + tl.arange(0, 64)
    block_col = tl.program_id(1)
    blk = row * blocks_per_row + block_col
    words = tl.load(packed_ptr.to(tl.pointer_type(tl.int32))
                    + blk[:, None] * 8 + tl.arange(0, 8)[None, :])
    q8 = tl.load(absmax_ptr + blk).to(tl.int32)
    scale = tl.load(code_ptr + q8) * tl.load(absmax2_ptr + blk // 256) + tl.load(offset_ptr)
    nib = tl.arange(0, 8)
    shift = 8 * (nib // 2) + 4 * (1 - nib % 2)
    q = (words[:, :, None] >> shift[None, None, :]) & 15
    values = (tl.load(nf4_ptr + q) * scale[:, None, None]).to(out_ptr.dtype.element_ty)
    values = tl.reshape(values, [64, 64])
    col = block_col * 64 + tl.arange(0, 64)
    tl.store(out_ptr + col[None, :] * rows + row[:, None], values)
```

Сетка запуска: `(rows // 64, cols // 64)`. Применять только к `gate` и `up`:

- forward: `torch.matmul(x, wt)`;
- backward: `torch.matmul(grad, wt.t())`.

Скорость разреженной записи в этом кернеле неизвестна, её нужно замерить отдельно против `nf4_unpack_wide_kernel`.

### 6.2. Идея 2: пересчёт без мёртвых значений

```python
# solution/mlp_tail.py
import torch

from . import linear4bit, stream
from .mlp_recompute import _in_backward
from .silu_mul import COLS_PER_PROGRAM, WARPS, _grid, silu_mul_kernel


def _adjoint(layer, grad):
    packed, absmax = stream.bytes_for(layer)
    state = layer.weight.quant_state
    weight = linear4bit._unpack(packed, state, state.dtype, absmax).to(grad.dtype)
    return torch.matmul(grad, weight)


class MlpTailRerun(torch.autograd.Function):
    """MLP in a rerun: only gate and up are computed, the output is a placeholder.
    Backward computes d = grad @ W_down, then the silu adjoint in place, then dx."""

    @staticmethod
    def forward(ctx, x, mlp):
        x16 = x.to(torch.float16)
        ctx.mlp, ctx.x_dtype = mlp, x.dtype
        ctx.gate = mlp.gate_proj(x16).contiguous()
        ctx.up = mlp.up_proj(x16).contiguous()
        return torch.zeros((), dtype=x.dtype, device=x.device).expand(x.shape)

    @staticmethod
    def backward(ctx, grad):
        gate, up, mlp = ctx.gate, ctx.up, ctx.mlp
        ctx.gate = ctx.up = None
        d = _adjoint(mlp.down_proj, grad.to(torch.float16)).contiguous()
        grid, n_cols = _grid(gate)
        silu_mul_kernel[grid](d, gate, up, gate, n_cols, COLS=COLS_PER_PROGRAM,
                              BACKWARD=True, num_warps=WARPS)
        del d
        dx = _adjoint(mlp.up_proj, up)
        del up
        dx += _adjoint(mlp.gate_proj, gate)
        return dx.to(ctx.x_dtype), None


def _probe(x, width):
    """A 1-element fp16 tensor expanded to [.., N, width]: the guards see the real shape, no memory."""
    one = torch.empty(1, dtype=torch.float16, device=x.device)
    return one.expand(*x.shape[:-1], width)


def _tail_ok(mlp, x):
    if not (isinstance(x, torch.Tensor) and x.is_cuda and x.dtype == torch.float32
            and mlp.training and torch.is_grad_enabled() and _in_backward()
            and stream.active()):
        return False
    layers = (mlp.gate_proj, mlp.up_proj, mlp.down_proj)
    if not all(layer.bias is None and stream.offloaded(layer) for layer in layers):
        return False
    return all(linear4bit._direct_ok(layer, _probe(x, layer.weight.quant_state.shape[1]))
               for layer in layers)


def patch_mlp_tail():
    from transformers.models.qwen2 import modeling_qwen2

    cls = modeling_qwen2.Qwen2MLP
    if getattr(cls, "_mindx_tail", False):
        return
    previous = cls.forward

    def forward(self, x):
        return MlpTailRerun.apply(x, self) if _tail_ok(self, x) else previous(self, x)

    cls.forward = forward
    cls._mindx_tail = True
```

`patch_mlp_tail()` нужно вызывать в `apply()` после `patch_qwen2_mlp_gateup_recompute()`.
